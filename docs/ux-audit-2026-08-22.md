# VacaVerse UX Audit — Cold-Eyes First-Time-User Pass

**Method:** Fresh accounts created through the real signup UI (no seed data existed). Two real accounts were used to test multi-person behavior: `dad.organizer@example.com` (organizer, created "The Schiffs" family + "Beach Week 2026" trip) and `grandma.audit@example.com` (joined "The Schiffs" via a real invite code generated in-app). Primary testing at a true mobile viewport (390×844, verified via `window.innerWidth`, using a Playwright-controlled browser — the claude-in-chrome extension's window could not be resized below ~820px in this environment, so it was used only for the second-account/multi-user session and cross-checks). A brief desktop pass was done at 1440×900. Screenshots referenced below are at `/Volumes/Workspace/Projects/VacaVerse/.claude/worktrees/bold-redesign/ux-audit-screens/`. Two transient tool/network errors interrupted the session (a dev-server kill and an MCP timeout on a clipboard read); both were infrastructure hiccups, not app behavior, and are not reported as findings.

App code referenced lives under `/Volumes/Workspace/Projects/VacaVerse/.claude/worktrees/bold-redesign/app/src/`.

## 1. Structural / Cross-Cutting Findings

### 1.1 — CRITICAL: Joining a family does not give you access to that family's trips
This is the core structural failure of the product. The entire pitch (PRODUCT.md) is "a whole family group gets a single shared place to plan a trip together," and it does not work end-to-end.

**What I did:** As `dad.organizer`, created family "The Schiffs," generated an invite code (`MS3KSD`), and had a second real account (`grandma.audit`) join via `/join` using that code. Family page then correctly showed "2 members." I then checked what grandma could see.

**What happened:** Grandma's Trips list shows "No trips found. Start planning one!" — even though dad's "Beach Week 2026" trip already exists and both users are in the same family (screenshots `13-family-detail.png`, and grandma's trips view). Navigating grandma directly to the trip URL (`/trips/LB8Ef-6jhTy6Ien2iz4Qw/polls`) returns a bare **"Trip not found"** screen — the same generic message used for a genuine loading race (see 2.7 below), so a user can never tell whether to wait/retry or whether they simply don't have access. In the Tasks "Assign to" dropdown, grandma does not appear as an assignable option at all, even after joining the family — only the trip's creator is listed (screenshot `21-add-task-modal.png`).

Root cause is visible from the client itself: trip creation (`Trips.tsx`) has no family picker at all, so a trip's `family_id` can go unset, and there is no "attach this trip to a family" control anywhere in the trip UI to fix that after the fact. Sharing a trip (the "Share trip" button) only produces a public **read-only, no-signup** preview link (`/trip/preview/:token`) — a completely separate mechanism from family membership, with its own "Sign In" / "Join the trip planning" CTAs that go to `/profile` and, per the above, still don't actually grant access to the trip (screenshot `29-trippreview.png`).

**Why it matters:** This breaks Product Principle #2 ("organizer's job is to disappear — distribute planning load") and the core value prop outright. A grandparent who does everything right — gets the code, joins the family — still cannot see, RSVP to, vote in, or be assigned anything on the one trip that family is planning. There is no error message, no "ask to be added to this trip," nothing — just silence and a generic "not found."

**Severity: Critical.**

### 1.2 — MAJOR: Trip planning and Family formation are unordered, with no bridge between them
**What I did:** Signed up as `dad.organizer`, and from a completely empty account went straight to Trips → "Plan a New Trip" and successfully created "Beach Week 2026" — with zero family in existence yet. The trip-creation modal (screenshot `05-new-trip-modal.png`) asks for Title/Start Date/End Date/Budget/Cover Image only; there is no family selector.

**Why it matters:** For a product whose entire premise is family-based planning, the onboarding path lets — even encourages, via the Home/Trips empty states — a user to build out a whole trip before a family group exists to share it with, with no prompt connecting the two and no way to retroactively attach a trip to a family. Compounds directly into 1.1.

**Severity: Major.**

### 1.3 — MAJOR: Inside a trip, two navigation systems show the same 8 destinations in two different orders
**What I did:** Opened any trip surface (e.g. Itinerary) and read both the top tab strip and the BottomNav in the same screen (screenshot `08-trip-itinerary-reload.png`, full DOM order confirmed via accessibility snapshot).

**What happened:**
- Top tab strip order: **Itinerary, Budget, Tasks, Feed, Notes, Search, Files, Polls**
- BottomNav order: **Itinerary, Feed, Notes, Search, Tasks, Budget, Files, Polls**

These are the identical 8 items in two different sequences, visible simultaneously on every trip page. The top strip also overflows the 390px viewport — only 6 of 8 labels are visible without a horizontal scroll (Files and Polls are off-screen to the right), while BottomNav shows all 8 at once via icon-only buttons with no visible text labels (compare to the outside-trip BottomNav, which does show icon+text: HOME/FAMILY/TRIPS/PROFILE).

**Why it matters:** Directly violates "every surface must work for the widest age range... without instruction." A grandparent or teenager who learns "Feed is the 2nd icon" on one nav has that expectation broken by the other nav on the same screen. The unlabeled 8-icon BottomNav (Itinerary/Comments/Notes/Search/Tasks/$/Folder/bar-chart icons) requires prior memorization to use — there is nothing on the icon itself (e.g. the bar-chart icon for "Polls," a folder for "Files") that a first-time user, of any age, could reliably decode.

**Severity: Major.**

### 1.4 — MAJOR: No desktop layout — the mobile stack is simply stretched full-width
**What I did:** Resized the browser viewport to 1440×900 (desktop) and loaded Home, Trips, and an open trip (screenshots `30-desktop-trip.png`, `31-desktop-home.png`).

**What happened:** `MainLayout.tsx` and `TripLayout` have no responsive breakpoint at all — the exact same single-column mobile layout (including the fixed BottomNav glued to the bottom of a 1440px-wide window) is used verbatim, just stretched, leaving enormous unused whitespace on both sides of every card, image, and list. There is no sidebar, no multi-column use of the extra space, nothing desktop-specific anywhere in the audited surfaces.

**Why it matters:** PRODUCT.md states "mobile is the primary usage scene, not an adaptation of desktop" — but the flip side, that desktop is still a supported platform, isn't met at all; what ships on desktop reads as an unfinished mobile app rather than a considered second layout.

**Severity: Major** (structural, but lower urgency than 1.1–1.3 since mobile is explicitly primary).

### 1.5 — MAJOR: The only sign-in/sign-up surface is the "Profile" tab, with no dedicated route
**What I did:** Loaded the app signed out; `App.tsx` routes show no `/login` or `/signup` route at all. `ProtectedRoute.tsx` redirects any unauthenticated visit to `/profile`, and `Profile.tsx` conditionally renders a full sign-in/sign-up form in place of the profile UI when `!user`.

**What happened:** The BottomNav is visible and fully tappable while logged out, including Home/Family/Trips — but tapping any of them silently bounces back to `/profile` with zero explanation (verified: clicked "Home" while signed out, URL stayed on `/profile`, no toast/message of any kind). The one tab that "works" is labeled **Profile**, which is a confusing frame for what is actually the app's front door — a first-time user has no reason to associate "Profile" with "this is where I create my account."

**Why it matters:** The very first interaction surface is mislabeled and the other three nav items are decoys that silently fail — exactly the kind of "figure it out yourself" moment the product principles say must not exist for any age group.

**Severity: Major.**

### 1.6 — MINOR: Repeated duplicate call-to-action pattern across empty states
**What I did:** Compared the empty states on Home, Trips, Tasks, and Notes.

**What happened:** Every one of these shows the exact same action twice: e.g. Trips has both a full-width "Plan a New Trip" button under the empty-state text *and* a floating "+" FAB in the bottom-right corner that does the same thing (screenshot `04-trips-empty.png`); Home has "Plan a Trip" plus the same FAB (`03-home-empty.png`); Tasks has "Add your first task" plus a header "Add task" button (`20-tasks-empty.png`); Notes has "Create your first note" plus a header "New note" button. The floating "+" FAB on Trips has no accessible name in the DOM (button with no text/aria-label — confirmed via accessibility snapshot, ref with no name).

**Why it matters:** Minor on its own, but it's a consistent pattern across 4+ surfaces, and for a cross-generational audience redundant, unlabeled controls add noise rather than help — a user has to decide which of two identical-looking buttons to use with no differentiation.

**Severity: Minor.**

## 2. Per-Surface Findings

### Sign Up / Sign In (`Profile.tsx`)
- **[Major]** Sign-up asks only for Email + Password — no display name field, no confirm-password field. Result: every new account defaults its display name to the email's local-part verbatim (e.g. "dad.organizer", "grandma.audit" shown as-is in the UI), which reads as a raw system artifact, not a name, everywhere it appears (Home header, Feed avatar, Profile).
- **[Major]** Immediately after signup, Home reads **"Welcome back, dad.organizer"** — "back" is wrong for a brand-new user's very first screen (screenshot `03-home-empty.png`).
- **[Minor]** No "Forgot password" link, no social/OAuth sign-in option.
- **[Minor]** `Profile.tsx:111` hardcodes a real stock photo URL (a specific woman's face from Unsplash) as the fallback avatar for any user without a `photo_url`, while `Home.tsx` falls back to initials for the same missing-photo case — two different, inconsistent fallback behaviors for the identical piece of state, and the Profile one assigns a stranger's actual face as a default identity image regardless of the user's own gender/appearance.

### Home
- **[Major]** "Welcome back" on a first-ever visit (see above).
- **[Minor]** Duplicate CTA pattern (see 1.6).

### Trips (list)
- **[Critical, supports 1.1]** Immediately after creating a trip and tapping into it from its own just-created card, the trip screen shows **"Trip not found"** (screenshot `07-trip-itinerary-empty.png`). A full page reload of the exact same URL then works correctly (screenshot `08-trip-itinerary-reload.png`) — this is a reproducible race condition where the newly created trip isn't yet in the in-memory trip list the detail route reads from. This means the single most natural next action after creating your first trip — looking at it — dead-ends on a "not found" error for every user, every time.
- **[Major]** "Delete Trip" is implemented as a hover-reveal icon: `className="... opacity-0 group-hover:opacity-100 ..."` (`Trips.tsx:31` for the hero card, `Trips.tsx:110` for the trip-rack cards). CSS `:hover` does not exist as a touch-device concept, so on the primary target platform (mobile/touch) this destructive control is **permanently invisible** — a user can only discover and trigger it by tapping blindly in the card's top-right corner. Measured DOM rect for this button: **32×32px**, below the 44px minimum PRODUCT.md claims is enforced app-wide. (It does call `confirm()` before actually deleting, so it isn't silently destructive once triggered — but it is invisible and undersized.) Note this exact anti-pattern is NOT used everywhere: `TripBudget.tsx:185` correctly guards the same pattern with `opacity-100 md:opacity-0 md:group-hover:opacity-100` (always visible below the `md` breakpoint), and `TripFeed.tsx`/`ThreadPanel.tsx` gate their reveal on a tap-toggled `actionsOpen` state rather than pure hover — so the fix pattern already exists elsewhere in the codebase, it's just missing on the Trips list.
- **[Minor]** "Budget $0" for a freshly created trip is correct behavior (the field starts empty; "5000" is a placeholder, not a submitted default) — flagged and ruled out, not a bug.

### Trip Creation Modal
- **[Major, supports 1.2]** No family selector (see 1.2).

### TripLayout header + tab strip (shared across all 8 trip surfaces)
- **[Major, supports 1.3]** Dual/misordered nav (see 1.3).
- **[Minor]** The hero image + title + Budget/Days-Away stat row + tab strip together consume roughly 40% of the 844px mobile viewport height on **every** sub-page, including chat-like Feed, which most benefits from vertical space. None of it collapses or shrinks on scroll or on navigating to a sub-tab.
- **[Minor]** Nav item is labeled **"Files"** in both navs, but the page itself is headed **"Documents"** and its route is `/documents` — three different names for the same surface.

### Itinerary
- **[Critical]** Verified, reproducible timezone/off-by-one date bug. Added an event with date `2026-09-11` (a Friday) via the native date input; the DB (`trip_events` table) correctly stores `2026-09-11`; but the UI groups and displays it under **"Thursday, September 10"** — one calendar day earlier than what was entered and what's stored (screenshots `16-itinerary-with-event.png`, and reproduced again on the public `TripPreview` page, `29-trippreview.png`, confirming it's a display/formatting bug, not a one-off). This is a date-parsing bug (classic UTC-midnight-parsed-then-formatted-in-local-timezone pattern) that would put a family's real itinerary on the wrong day.
- **[Minor]** Times are shown in 24-hour format ("18:00") with no AM/PM, which is less immediately parseable for part of a US-centric, cross-generational audience.
- **[Minor]** Toast confirmation ("Event added") renders low enough on screen to visually overlap the floating "+" FAB and peek over the BottomNav icon row (screenshot `16-itinerary-with-event.png`) — a z-index/layout collision among fixed-position elements.

### Feed
- **[Works reasonably well.]** Posting a message worked correctly and appeared instantly with a timestamp (screenshot `19-feed-posted.png`). Split into "Comments" / "Activity" tabs with counts, which is reasonable.
- **[Minor]** Because of the tall shared trip header (see above), the actual message thread has very little vertical room on a 390px-wide phone before the message list starts scrolling.
- Could not verify how a second family member's comments render inline (see Section 4 — testing limitation), since grandma could never reach this trip's Feed at all (see 1.1).

### Tasks
- **[Critical, supports 1.1]** "Assign to (optional)" dropdown lists only "Unassigned" and "dad.organizer" — a fellow family member (grandma, already joined "The Schiffs") is not selectable, because trip membership is tracked separately from family membership and she was never added to this trip (screenshot `21-add-task-modal.png`). This directly breaks the "distribute planning load across the whole family" principle at the one surface built specifically for that job.
- **[Minor]** Duplicate CTA pattern (see 1.6).

### Budget
- **[Fine on this pass.]** Empty state, "Total Spent / Remaining" summary, and "Expenses by Category" / "Recent Expenses" sections all render sensibly with clear empty-state copy (screenshot `22-budget-empty.png`). No expense was added in this pass beyond viewing the empty state; no problems observed structurally.

### Documents ("Files" in nav)
- **[Minor, supports label-inconsistency finding above.]** Otherwise a clean, simple empty state (screenshot `23-documents-empty.png`).

### Notes
- **[Minor]** Duplicate CTA pattern (see 1.6). Did not create a note to test the TipTap editor itself in this pass; empty state is otherwise clear (screenshot `24-notes-empty.png`).

### Polls
- **[Works.]** Poll creation flow (question + 2 options + "Add Option") is straightforward and worked correctly on the first try (screenshots `25-polls-empty.png`, `26-poll-created.png`).
- Could not test actual multi-person voting, since grandma could not reach this trip at all (see 1.1 and Section 4).

### Search (in-trip)
- **[Works.]** Query "sunscreen" correctly surfaced the matching task with the term highlighted (screenshot `28-search-results.png`).
- **[Minor]** Scope is explicitly limited to "comments, tasks, and notes" (per the placeholder text and empty-state copy) — it does not search itinerary events, budget/expenses, documents, or polls, despite being presented as a general trip search with no visible scope indicator once you're inside a specific trip's Search tab.

### TripPreview (public share link)
- **[Major, supports 1.1]** Reproduces the itinerary date-display bug (see above). Both its "Sign In" and "Join the trip planning" CTAs route to `/profile` — and given 1.1, actually completing that sign-in still does not grant access to this trip. The promise ("Join the trip planning") is not backed by the mechanism it links to.
- **[Minor]** The public share token is generated client-side as `crypto.randomUUID().slice(0, 12)` (`TripLayout.tsx:57`) — a 12-character slice of a UUID for a link explicitly described as "Anyone with this link can view the itinerary without signing in." Noted as a minor, code-visible design detail, not tested as an exploit.

### Family
- **[Works reasonably well.]** Create-family, invite-code generation ("Get Invite Code" → 6-character code, "Expires in 7 days"), and join-by-code (tested end-to-end with a second real account) all functioned correctly and are one of the smoother flows in the app (screenshots `10`–`14`).
- **[Note, not scored]** PRODUCT.md's capability list mentions a "visual family tree builder"; the Family surface as built is a flat member list with no relationship/tree UI. Flagging as an observation since it may be intentionally out of scope for this pass rather than a regression.

### Join (`/join`)
- **[Works.]** Code entry → confirmation card ("Would you like to join this family group?") → join, worked cleanly end-to-end (screenshots `13`, and the claude-in-chrome join sequence).

### Profile (signed-in state)
- **[Major]** Every secondary control is a dead end: "Edit Profile," the header "Settings" gear, and all four menu rows (Notifications — which shows a "3" badge implying real unread notifications that don't exist anywhere in the app, Payment Methods, Privacy & Security, Help & Support) have no `onClick` handler at all (confirmed in `Profile.tsx` — only `toggleTheme`, the sign-up/sign-in toggle, and `logout` have handlers). These render as fully-styled, chevron-affordanced, seemingly-functional rows that do nothing when tapped.
- **[Works]** Dark/Light mode toggle is real and functional.
- **[Works]** Logout is real and functional.

## 3. Worst-to-Best Severity Ranking (surfaces + onboarding)

1. **Family ↔ Trip integration (cross-cutting)** — Critical. Core value prop doesn't function past 2 people.
2. **Onboarding path (signup → first trip → first family)** — Critical. No dedicated auth route, ordering trap between Trip and Family creation, "Trip not found" on the very first trip you open.
3. **Trips (list)** — Critical/Major. Race-condition "Trip not found" bug + invisible/undersized delete control.
4. **Tasks** — Critical (for the family-collaboration promise specifically) — assignment is unreachable for real family members.
5. **Itinerary** — Critical — wrong-day display bug, reproduced in two places.
6. **TripPreview** — Major — inherits the itinerary bug and makes a promise ("join the trip planning") the app can't keep.
7. **In-trip navigation (top tabs + BottomNav, cross-cutting)** — Major — redundant, misordered, partly-hidden nav.
8. **Profile (signed-in)** — Major — most of the surface is non-functional decoration.
9. **Desktop layout (cross-cutting)** — Major — effectively unbuilt, mobile stack stretched.
10. **Home** — Major/Minor — wrong greeting copy, duplicate CTAs.
11. **Notes** — Minor — only the duplicate-CTA pattern observed; editor itself untested.
12. **Documents/"Files"** — Minor — label inconsistency only.
13. **Search** — Minor — works, but scope is narrower than it appears.
14. **Budget** — Minor/None — worked cleanly on this pass.
15. **Feed** — Minor/None — worked cleanly on this pass (posting, tabs); limited by inability to test a second voice.
16. **Polls** — Minor/None — creation worked cleanly; limited by inability to test voting with a second voice.
17. **Family** — Minor/None — the smoothest flow in the app.
18. **Join** — Minor/None — worked cleanly end-to-end.

## 4. Testing Limitations

- **Multi-person surfaces (Feed comments, Poll voting, Task assignment, itinerary RSVPs from more than one person) could not be genuinely tested with two collaborating voices.** A second real account (`grandma.audit@example.com`) was created and successfully joined the same family via a real invite code — but, as documented in Finding 1.1, family membership does not grant trip access, so that second account could never actually open the trip to comment, vote, or be assigned anything. This is itself the most important structural finding of the audit, but it also means Feed/Polls/Tasks were only exercised single-handedly as the organizer.
- **Notes editor (TipTap) content and formatting were not exercised** — only the empty state was observed; no note was created.
- **Document upload was not exercised** — only the empty state was observed.
- **Expense entry (Budget) was not exercised** — only the empty state was observed.
- **True mobile-viewport testing used a Playwright-controlled browser rather than the claude-in-chrome extension**, because the extension's window could not be resized below ~820×615px in this environment (repeated `resize_window` calls had no effect on `window.innerWidth`). The claude-in-chrome browser was still used successfully for the second real account and cross-checks. Playwright's viewport (390×844) was verified directly via `window.innerWidth`/`innerHeight` before testing began.
